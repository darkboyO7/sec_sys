## 3. Implement evidence-based control evaluation

Build a deterministic evaluation engine that compares available authorized evidence with applicable controls.

Use explicit result states such as:

- `PASS`: sufficient valid evidence demonstrates that the defined requirement is satisfied.
- `FAIL`: sufficient valid evidence demonstrates that the requirement is not satisfied.
- `PARTIAL`: evidence supports only part of the requirement.
- `UNKNOWN`: evidence is insufficient to decide.
- `NOT_APPLICABLE`: documented applicability rules establish that the control does not apply.
- `ERROR`: evaluation could not be completed reliably.

Do not treat `UNKNOWN`, `PARTIAL`, or `ERROR` as a pass.

Each result must preserve:

- Control ID and control version.
- Assessment or evaluation run ID.
- Evaluation timestamp.
- Applicable assets or resources.
- Evidence references and integrity metadata.
- Evaluation method and version.
- Reasoning based on the actual evidence.
- Missing evidence requirements.
- Confidence or certainty, where supported by the existing architecture.
- Any known evaluation limitations.

Use deterministic, testable rules for compliance decisions. If AI assistance is available, it may help explain a result, but it must not override evidence requirements or independently promote an uncertain result to `PASS`.

## 6. Build configuration-drift detection

Compare new observations and compliance results against a recorded, trusted prior state.

Detect meaningful changes such as:

- A previously passing control becomes failing.
- A control becomes unknown because required evidence disappears.
- A new applicable control is introduced by a baseline revision.
- An asset becomes newly exposed or materially changes state.
- An approved exception expires or is revoked.
- Evidence freshness exceeds an explicitly configured threshold.
- A previously failed control passes after independently verified remediation.

Preserve both the previous and new states, timestamps, source evidence, and reason for the change.

Distinguish actual configuration drift from evidence drift. For example, a missing observation should not automatically be described as proof that a configuration changed.

Make drift detection idempotent so repeated ingestion of identical evidence does not create unlimited duplicate events.

Integrate with existing event and alerting services if present. Do not create a separate notification engine unnecessarily.
