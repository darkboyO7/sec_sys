## 3. Strengthen authentication and authorization testing

Create tests that exercise the actual server-side enforcement points.

Verify that:

- Unauthenticated requests cannot access protected resources.
- Authenticated users cannot exceed their assigned permissions.
- Read-only users cannot perform unauthorized mutations.
- Users cannot access another user's or tenant's resources where isolation is required.
- Resource identifiers cannot be changed to bypass ownership or scope checks.
- Client-side authorization state never substitutes for server-side authorization.
- Missing, malformed, expired, or invalid credentials fail safely.
- Unauthorized requests do not cause partial writes or privileged side effects.
- Authorization errors do not disclose unnecessary sensitive information.

Use separate test identities and persisted records. Test both allowed and denied operations.

Avoid testing authorization exclusively through mocked permission functions; at least the critical API-level checks must traverse the actual authentication and authorization middleware or dependency chain.

If the application is intentionally single-user and local, validate its real access-control model rather than adding unnecessary multi-user architecture merely to satisfy this prompt.

## 4. Verify assessment scope and target safety

Exercise the real policy-enforcement path with synthetic targets and controlled fixtures.

Test:

- In-scope versus out-of-scope target decisions.
- Explicit exclusions overriding broader inclusions.
- Missing or invalid authorization evidence.
- Unverified DNS results or unresolved targets.
- Policy changes between job submission and execution.
- Scope changes while a job is queued.
- Attempts to bypass scope restrictions through alternate API routes or direct service calls.
- Attempts to submit malformed or ambiguous targets.
- Cancellation and failure behavior when authorization can no longer be established.

Use deterministic fake resolvers and simulated assessment adapters. Do not perform unauthorized network testing or introduce disruptive traffic.

Where real network adapters exist, use controlled local fixtures and confirm that every outbound operation is preceded by the appropriate server-side authorization and target validation.

## 5. Add mutation testing for critical security controls

Inspect available mutation-testing tools and choose an approach compatible with the current Python and TypeScript projects.

Use mutation testing to evaluate whether tests would detect deliberate changes such as:

- Replacing an authorization check with unconditional permission.
- Reversing a scope inclusion or exclusion decision.
- Accepting an unverified target.
- Bypassing an approval requirement.
- Treating a failed evidence-integrity check as successful.
- Skipping an audit-chain consistency check.
- Marking a failed retest as passed.
- Accepting an invalid recovery postcondition.
- Removing a required server-side validation.
- Allowing a failed release-integrity check to pass.

Apply mutations only in disposable working copies, isolated test fixtures, or tool-managed temporary files. Never deliberately weaken the main application's production code and leave the change behind.

For every critical mutation, demonstrate that the relevant test suite fails for the intended reason. If a mutation survives, investigate the missing assertion and add a meaningful test where appropriate.

Do not game mutation scores with assertions that merely detect implementation text or with tests that duplicate the implementation's logic without independently checking its behavior.

Begin with a focused set of high-impact mutations. Expand coverage only when results demonstrate value.

## 6. Verify audit integrity and evidence handling

Create tests for the complete evidence lifecycle where supported:

- Evidence creation and persistence.
- Stable digest generation.
- Retrieval and integrity verification.
- Detection of altered stored evidence.
- Detection of missing or inconsistent provenance.
- Audit-chain ordering and predecessor-hash verification.
- Rejection or explicit handling of malformed audit events.
- Preservation of conflicting observations.
- Failure behavior when integrity verification is unavailable.
- Correct attribution of the actor and operation.

Verify that rejected or tampered evidence cannot silently become trusted input to risk calculations or remediation decisions.

Use synthetic evidence and deterministic fixtures. Never use real customer data or actual secrets in tests.

## 7. Test remediation and recovery as stateful workflows

Exercise complete transitions rather than isolated helper functions.

For remediation, verify:

- A finding cannot bypass required approval.
- Approval is bound to the intended action and scope.
- Rejected or expired approvals cannot be reused.
- Duplicate submissions do not cause unsafe repeated side effects.
- Failed execution is recorded honestly.
- Independent retesting cannot merely reuse the original expected result.
- A failed retest does not mark the finding resolved.

For recovery, verify:

- Preconditions are checked before changes occur.
- Invalid recovery plans fail safely.
- Rollback or compensation behavior is correct when supported.
- Postconditions are independently checked.
- Partial failure is visible and does not produce a false success state.
- Audit history remains consistent after recovery.
- Security policies and assessment scope are never relaxed to make recovery succeed.

Use fake execution adapters and disposable test databases. Never perform destructive recovery against user data or real infrastructure.

## 8. Test transaction integrity and concurrency

Exercise the database and background-job paths under controlled concurrent activity.

Include:

- Simultaneous updates to the same finding.
- Duplicate job submissions.
- Competing remediation approvals or state transitions.
- Concurrent evidence insertion and audit-chain updates.
- Database lock and transient transaction failures.
- Worker termination during a state transition.
- Application restart with queued or abandoned jobs.
- Retry behavior after partial completion.
- Conflicting updates and stale-version handling.

Assert the final persisted state, not just the returned HTTP response.

Verify that the system cannot silently lose evidence, create contradictory terminal states, bypass approval, or mark incomplete work as successful.

Keep concurrency tests deterministic and bounded. Avoid relying on arbitrary sleeps or timing assumptions when synchronization primitives and explicit barriers can be used.

## 9. Verify frontend and API contract integrity

Add tests that detect mismatches between frontend assumptions and actual backend behavior.

Where applicable, cover:

- API request and response schema validation.
- Missing or renamed response fields.
- Validation errors and unauthorized responses.
- Stale asynchronous responses overwriting current state.
- Duplicate submissions caused by repeated interactions.
- Loading, empty, error, and retry states.
- Server-side authorization when the UI displays privileged controls.
- Correct display of failed, incomplete, and unverified security operations.

Ensure the frontend cannot present an operation as successful simply because a request was submitted.

Use the actual API contract and existing test infrastructure. Avoid introducing a second incompatible source of truth for schemas.

## 10. Detect ineffective tests and improve coverage quality

Review the suite for:

- Assertions that are absent or too weak.
- Tests that always pass due to swallowed exceptions.
- Unexpectedly skipped tests.
- Fixtures that bypass the security behavior under test.
- Over-mocking of authorization or persistence.
- Shared state that makes tests order-dependent.
- Tests that require external services without clear isolation.
- Tests that pass while expected database writes never occur.
- Security checks covered only by happy-path tests.
- Unstable concurrency tests.
- Coverage exclusions that hide critical code.

Use branch coverage where supported and meaningful, but do not treat a single coverage percentage as proof of security.

Define targeted minimum expectations for critical control modules based on the baseline. Avoid arbitrary repository-wide thresholds that encourage meaningless assertions or make unrelated changes unnecessarily difficult.

## 11. Integrate a practical security regression gate

Integrate the verification suite into existing local scripts and CI where present.

The gate should:

1. Run deterministic unit tests.
2. Run critical API and integration tests.
3. Run database and stateful workflow tests.
4. Run frontend tests and contract checks.
5. Execute the selected critical mutation tests where practical.
6. Report skipped tests and missing tools explicitly.
7. Fail when required security-control tests fail.
8. Preserve diagnostic output without exposing secrets.
9. Distinguish test failures from environment or dependency failures.
10. Produce a machine-readable summary of the verification results.

Keep ordinary development tests reasonably fast. Separate slower mutation and stress suites into explicit commands or scheduled jobs if necessary, while ensuring critical security regression tests remain mandatory.

Do not convert failed tests into skips merely to make the gate green.
