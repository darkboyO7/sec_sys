## 2. Establish one validated configuration system

Inspect whether backend settings are scattered across modules or loaded inconsistently.

Where necessary, implement a central, typed configuration layer that provides:

- Explicit configuration sources and documented precedence.
- Validation of required and optional values.
- Clear distinction between development, testing, and production modes.
- Safe defaults for security-sensitive settings.
- Strict parsing of booleans, integers, durations, URLs, paths, and enumerated values.
- Validation of filesystem paths and writable directories.
- Consistent configuration access throughout the application.
- A redacted configuration diagnostic that shows effective non-secret settings without revealing secret values.

Requirements:

1. Reject malformed security-sensitive configuration instead of silently falling back to unsafe defaults.
2. Never substitute a known or predictable production secret when configuration is missing.
3. Avoid duplicate configuration implementations that disagree about effective values.
4. Preserve testability through explicit test configuration and synthetic credentials.
5. Keep local development straightforward with clearly documented example configuration.
6. Avoid silently changing existing environment-variable names unless compatibility and migration are handled deliberately.

Do not print secret values in validation errors, logs, exception messages, or diagnostic output.

## 3. Harden first-run initialization and secret handling

Inspect how the application creates its initial configuration, authentication material, signing keys, and database.

Implement appropriate protections so that:

- First-run setup does not create publicly known production credentials.
- Development-only convenience defaults cannot accidentally become production settings.
- Required secrets are generated or provisioned through a documented secure mechanism where appropriate.
- Secret generation uses cryptographically secure randomness.
- Secret files are not committed to Git or included in release archives.
- Existing valid secrets are not silently overwritten during restart or upgrade.
- Secret rotation behavior is documented and tested.
- Missing or invalid secrets cause a clear startup failure when the affected security feature requires them.
- Sensitive diagnostic information is redacted.
- Example configuration files contain placeholders, never actual credentials.

Do not rotate existing secrets automatically on every startup. Do not invalidate existing user sessions or data without an explicit, documented migration or rotation procedure.

## 4. Secure the local network exposure model

Review backend and frontend binding behavior and the actual deployment assumptions.

Verify that:

- Local-only operation binds to loopback by default where appropriate.
- Binding to a network interface requires an explicit, documented configuration choice.
- A frontend development server does not become an unintended public service.
- CORS uses deliberate allowed origins rather than broad wildcard defaults when credentials are involved.
- Host-header validation and trusted-host protections are appropriate for the deployment.
- Forwarded headers are trusted only when supplied by explicitly configured trusted proxies.
- Browser-facing session and authentication protections are consistent with the existing authentication architecture.
- Debug mode, interactive documentation, and development-only endpoints are not accidentally exposed in production mode.
- Health and diagnostic endpoints reveal no secrets, filesystem internals, tokens, or sensitive assessment data.
- API security does not depend on the frontend hiding controls.

Do not introduce unnecessary networking complexity into the local application. Document precisely what is and is not exposed under each supported operating mode.

## 5. Harden Windows filesystem behavior

Review all paths used for configuration, SQLite databases, logs, evidence, exports, backups, and temporary files.

Implement appropriate safeguards against:

- Accidental writes outside designated application data directories.
- Path traversal through user-controlled filenames or export destinations.
- Confusing relative paths that resolve differently depending on the current working directory.
- Unexpected symbolic links or reparse-point behavior where relevant.
- Overly broad file permissions.
- Sensitive temporary files left behind after failures.
- Log and evidence paths colliding with source or configuration files.
- File-locking issues and unsafe concurrent file replacement.
- Sensitive data included in temporary archives.

Use robust path handling compatible with supported Windows environments. Avoid hardcoding developer-specific absolute paths into application runtime logic.

Where permission enforcement is practical, use least-privilege Windows file and directory permissions. Do not claim permissions are secure without checking the actual behavior of the implementation and its deployment instructions.

Preserve legitimate user data. Never run broad recursive deletion or destructive cleanup as part of setup.

## 6. Implement a safe startup preflight

Create or strengthen a startup validation process that checks prerequisites before the application accepts work.

Where relevant, validate:

- Required configuration values.
- Dependency and runtime compatibility.
- Database connectivity.
- Alembic migration state.
- Required data directories and their writability.
- Essential cryptographic configuration.
- Required frontend build artifacts in production mode.
- Existing lock files and signs of interrupted initialization.
- Security-critical configuration combinations.
- The availability of required local services.

Separate fatal startup conditions from warnings and optional capabilities.

Examples of fatal conditions include invalid required secrets, a broken database schema, or a security configuration that would invalidate a mandatory authorization guarantee.

Examples of warnings include unavailable optional monitoring integrations.

The preflight must not report success merely because a process started. It must verify the conditions needed for safe operation.

Do not perform automatic destructive repair when a check fails. Provide an actionable error and a safe recovery path.

## 7. Make database initialization and upgrades safe

Inspect the current database and migration lifecycle.

Implement appropriate protections for:

- First-time database creation.
- Alembic migration execution and head validation.
- Interrupted migration handling.
- Concurrent startup attempts.
- Existing databases with pending migrations.
- Incompatible or unknown schema versions.
- Backup requirements before risky schema changes.
- Data integrity checks after migrations.
- Recovery when migration execution fails.

Requirements:

1. Do not silently recreate or reset an existing database.
2. Do not treat an empty database as proof that the intended database was selected.
3. Avoid running competing migrations concurrently.
4. Make upgrade failures visible and actionable.
5. Preserve existing records and relationships.
6. Use explicit migration scripts for schema changes.
7. Test upgrades from representative prior schema states where practical.
8. Clearly distinguish schema migration from data recovery or restoration.

If automatic migration on startup is inappropriate for the current architecture, provide an explicit upgrade command and ensure startup reports the required action clearly.

## 9. Implement a safe upgrade and rollback protocol

Develop a documented, tested upgrade procedure appropriate to the current architecture.

A normal upgrade should:

1. Verify the existing installation and required configuration.
2. Check disk space and required dependencies where practical.
3. Create a verified backup when the upgrade could affect persistent data.
4. Validate the target version and migration plan.
5. Prevent conflicting upgrade operations.
6. Apply the upgrade through controlled steps.
7. Run post-upgrade schema and application checks.
8. Report success only after the required checks pass.
9. Preserve enough diagnostic information to investigate failures.
10. Provide a recovery procedure for a failed upgrade.

Do not assume rolling back application files automatically rolls back database migrations. Define separate recovery behavior for code, schema, configuration, and persistent data.

Never automatically restore an old database over newer user data without explicit authorization and verified recovery conditions.

If a fully automatic rollback cannot be made safe, implement a clear manual recovery procedure rather than pretending rollback is reliable.
